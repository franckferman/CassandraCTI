Introduction

CassandraCTI Documentation

CassandraCTI is a modular, asynchronous Cyber Threat Intelligence aggregator. It collects events from multiple sources, deduplicates them via SHA1 fingerprinting, routes them through configurable rules, renders messages from Jinja2 templates, and delivers them to Microsoft Teams, Discord, Telegram, or email (SMTP).

Named after the Trojan prophetess condemned to warn without being believed — CassandraCTI makes sure your threat intel actually reaches the people who need it.

Pipeline at a glance

Sources   RSS / Atom · ransomware.live · Red Flag Domains
          ransomware.press · ransomware.8k · ransomware.stats (PRO)
   ↓
Filter    regex deny/allow · max_items_per_source · date filter
   ↓
Dedupe    SHA1(source + url|title) → SQLite event store
   ↓
Route     source prefix · tag match · regex (title / source) — all-match
   ↓
Render    Jinja2 templates per route
   ↓
Send      Teams · Discord · Telegram · Email (SMTP)  (retry + throttle)
Getting Started

Installation

Requirements

  • Python 3.10 or later
  • pip

From source

# Clone the repository
git clone https://github.com/franckferman/CassandraCTI.git
cd CassandraCTI

# Install dependencies
pip install -r requirements.txt

# Or install as a package (installs the cassandra CLI entry point)
pip install .

Configuration directory

By default, CassandraCTI looks for its configuration in a platform-specific directory:

PlatformPath
Linux~/.config/cassandra-cti/ (or $XDG_CONFIG_HOME/cassandra-cti/)
macOS~/Library/Application Support/cassandra-cti/
Windows%APPDATA%\cassandra-cti\

The directory contains two files:

~/.config/cassandra-cti/
├── config.yaml         ← sources, routes, filters, store, metrics
├── connectors.yaml     ← transport definitions (webhook URLs)
└── templates/          ← custom Jinja2 templates (optional)
Getting Started

Quick Start

In a hurry? cassandra quickstart scaffolds the config files and opens the live dashboard in one command. The steps below wire up alerting to Teams/Discord/Telegram/email.

1. Initialize config files

cassandra init

2. Add a connector

# --type: teams (default) | discord | telegram | smtp
cassandra add-connector --id "teams-soc" --type teams \
  --webhook-url "https://your-tenant.webhook.office.com/..." --theme-color "0078D7"

cassandra add-connector --id "tg-soc" --type telegram \
  --bot-token "$TELEGRAM_BOT_TOKEN" --chat-id "@my_channel"

3. Add threat intel sources

# RSS feed
cassandra add-source rss \
  --name "CERT-FR Alertes" \
  --url "https://cert.ssi.gouv.fr/alerte/feed/" \
  --tags "cert,fr"

# Ransomware · domains · CVEs (CISA KEV) · IOCs (abuse.ch)
cassandra add-source ransomware_live
cassandra add-source redflag
cassandra add-source kev
cassandra add-source abusech --feeds "feodo,urlhaus"

4. Validate configuration

cassandra doctor config
cassandra doctor connector --id teams-soc

5. Run

# One-shot
cassandra run

# Loop every 5 minutes
cassandra run --loop --interval 300

# Serve the live dashboard (implies --loop)
cassandra run --web

# Dry run (no messages sent)
cassandra run --dry-run --verbose
Configuration

config.yaml

The main configuration file. Controls sources, routing, filtering, storage, and metrics. Supports ${VAR_NAME} environment variable substitution anywhere in the file.

config.yaml — full reference
schema_version: 1

scheduler:
  mode: oneshot          # "oneshot" | "loop"
  interval_seconds: 300  # used when mode: loop

sources:
  rss:
    enabled: true
    feeds:
      - name: "CERT-FR Alertes"
        url: "https://cert.ssi.gouv.fr/alerte/feed/"
        tags: ["cert", "fr"]
  ransomware_live:
    enabled: true
    lookback_days: 30      # how far back to fetch attacks
    api_key: ${RANSOMWARE_API_KEY}  # optional PRO tier → falls back to v2 → posts.json
    url: "..."              # optional posts.json override
  ransomware_press:        # PRO-only cyber-press news feed (no fallback)
    enabled: false
    api_key: ${RANSOMWARE_API_KEY}
  ransomware_8k:           # PRO-only: SEC 8-K cyber-incident filings
    enabled: false
    api_key: ${RANSOMWARE_API_KEY}
  ransomware_stats:        # PRO-only: one daily tracker digest
    enabled: false
    api_key: ${RANSOMWARE_API_KEY}
  red_flag_domains:
    enabled: true
    base_url: "..."         # optional override

filters:
  title_regex_deny:       # drop events whose title matches
    - "(?i)sponsored"
    - "(?i)webinar"
  title_regex_allow: []   # if non-empty, ONLY pass matching titles
  max_items_per_source: 50

transports:
  use: ["teams-soc", "discord-alert"]  # reference connector IDs

routes:
  - name: "cert-alerts"
    include_tags: ["cert"]
    transports: ["teams-soc"]
    template: "templates/rss_default.j2"   # optional

store:
  sqlite_path: ".cassandra_cti.db"
  seen_ttl_days: 90       # purge events older than N days

logging:
  level: "INFO"           # DEBUG | INFO | WARNING | ERROR

metrics:
  enabled: true
  host: "127.0.0.1"       # localhost by default; set 0.0.0.0 to expose
  port: 9108

Transports reference

KeyDescription

Routes

Every matching route fires — a single event can fan out to several routes at once. Per-transport deduplication guarantees the same event is never delivered twice to the same transport. An event not matched by any route is silently dropped.

KeyTypeDescription
namestringUnique route identifier (used in logs).
include_sourceslist[str]Match by source ID prefix or exact name. e.g. rss: matches all RSS feeds.
include_tagslist[str]Match if any event tag is in this list.
include_regexstringPython regex tested against title and source.
transportslist[str]Connector IDs to deliver matched events to.
templatestringPath to a Jinja2 template file. Optional — falls back to transport default.

KeyTypeDefaultDescription
sqlite_pathstring.cassandra_cti.dbPath to the SQLite deduplication database. Relative paths are resolved from the config file directory.
seen_ttl_daysint90Events older than this are purged on each run. Set to 0 to disable.

Configuration

connectors.yaml

Defines transport instances (webhook endpoints, formatting options). Kept separate from config.yaml so it can be secrets-managed independently. Supports ${VAR_NAME} substitution.

connectors.yaml
connectors:
  - id: "teams-soc"
    type: "teams"
    params:
      webhook_url: ${MSTEAMS_WEBHOOK_SOC}
      theme_color: "0078D7"
      emojis: true
      throttle_ms: 1000
      batching:
        enabled: true
        max_items: 5

  - id: "discord-alert"
    type: "discord"
    params:
      webhook_url: ${DISCORD_WEBHOOK_URL}
      username: "CassandraCTI"
      avatar_url: "https://..."
      emojis: true
      throttle_ms: 500

  - id: "telegram-soc"
    type: "telegram"
    params:
      bot_token: ${TELEGRAM_BOT_TOKEN}
      chat_id: ${TELEGRAM_CHAT_ID}   # "@publicchannel" or -100123456789
      parse_mode: "HTML"           # default; falls back to plain text on parse errors
      emojis: true
      throttle_ms: 1000

  - id: "email-soc"
    type: "smtp"
    params:
      host: ${SMTP_HOST}            # e.g. smtp.gmail.com
      port: 587
      security: "starttls"         # starttls (587) | ssl (465) | none (25)
      username: ${SMTP_USERNAME}
      password: ${SMTP_PASSWORD}    # app password / API key
      from_addr: ${SMTP_FROM}       # defaults to username
      to_addrs: ${SMTP_TO}          # "a@x.com,b@y.com" or a YAML list
      subject_prefix: "[CTI]"

Telegram connector params

Unlike Teams/Discord there is no incoming-webhook URL. Sending is a POST to the Bot API sendMessage endpoint, so a bot_token and a chat_id are required.

ParamTypeRequiredDescription
bot_tokenstringYesBot token from @BotFather (/newbot).
chat_idstring / intYesTarget chat: a public @channelusername or a numeric id (e.g. -100123456789). Add the bot to the channel/group as an administrator.
parse_modestringNoMessage formatting. Default: HTML. Falls back to plain text automatically if Telegram rejects the entities.
emojisboolNoPrepend computed emoji to the message title. Default: true.
emoji_mapdictNoCustom source_id → emoji overrides.
disable_web_page_previewboolNoSuppress link previews. Default: true.
throttle_msintNoMinimum ms between sends. Default: 1000.
batching.enabledboolNoGroup multiple events into a single message.
batching.max_itemsintNoMax events per batched message.

Messages render as HTML with a 4096-char limit (auto-truncated). On a 429 the transport honours Telegram's retry_after and backs off. Assign a Telegram-flavoured template (e.g. templates/telegram_default.j2) — Teams/Discord Markdown won't render as rich text on Telegram.

SMTP (email) connector params

Sends HTML email through any SMTP server using the Python standard-library smtplib (no extra dependency). The body is a multipart/alternative message (plain text + HTML).

ParamTypeRequiredDescription
hoststringYesSMTP server hostname (e.g. smtp.gmail.com).
portintNoSMTP port. Default: 587.
securitystringNostarttls (587, default) · ssl (implicit TLS, 465) · none (plaintext, e.g. an internal relay on 25).
usernamestringNoSMTP auth username. Login is skipped if username/password are omitted.
passwordstringNoSMTP auth password / app password / API key.
from_addrstringNoEnvelope sender. Defaults to username.
to_addrsstring / listYesRecipients: "a@x.com,b@y.com" or a YAML list.
subject_prefixstringNoPrepended to the subject line. Default: [CTI].
emojisboolNoPrepend computed emoji to the subject. Default: true.
throttle_msintNoMinimum ms between sends. Default: 1000.
batching.enabledboolNoGroup events into a single digest email.
batching.max_itemsintNoMax events per digest email.

Gmail example: host smtp.gmail.com, port 587, security starttls, username = your address, password = a Google App Password (not your login password). Batching is recommended so you receive one digest instead of one email per event.

Configuration

Environment Variables

Runtime behavior can be overridden via environment variables without touching config files.

VariableDescription
CTI_CONNECTORSOverride path to connectors.yaml.
CTI_LOGLEVELOverride log level at runtime: DEBUG, INFO, WARNING, ERROR.
CTI_SINCEOnly process events published after this ISO8601 date (e.g. 2025-03-01). Overrides --since flag.
CTI_NO_DEDUPESet to any non-empty value to skip deduplication entirely.
CTI_DRY_RUNSet to any non-empty value to log delivery actions without sending anything.
CTI_TLS_NO_VERIFYSet to 1 to disable TLS certificate verification on all fetches (for intercepting corporate proxies). TLS is verified by default.
ABUSECH_API_KEYabuse.ch Auth-Key — unlocks the ThreatFox & MalwareBazaar feeds (Feodo/URLhaus work without it).
ANTHROPIC_API_KEY / OPENAI_API_KEY / DEEPSEEK_API_KEYOptional cloud keys for the LLM layer (AI briefs & briefings). Not needed with a local Ollama.
CTI_WEB_TOKENOptional Bearer / ?token= auth for the web dashboard when exposed beyond localhost.
SIGNAL_NUMBERSignal sender number registered on your signal-cli-rest-api bridge.

Config files also support ${VAR_NAME} substitution, which is resolved at load time. Use this to inject webhook URLs, bot tokens, API keys, and other secrets without committing them to disk:

connectors:
  - id: "teams-soc"
    type: "teams"
    params:
      webhook_url: ${MSTEAMS_WEBHOOK_SOC}

sources:
  ransomware_live:
    api_key: ${RANSOMWARE_API_KEY}

Secure by default. HTTP fetches are TLS-verified (opt out with CTI_TLS_NO_VERIFY=1), response bodies are size-capped at 25 MiB, and the Prometheus metrics server binds 127.0.0.1 unless you set metrics.host to 0.0.0.0. A PRO api_key left as an unexpanded ${VAR} placeholder is treated as no key.

Sources

Ransomware Live

Tracks ransomware group attacks from ransomware.live. Each attack becomes a deduplicated event with rich metadata. The source uses a resilient multi-backend fallback chain: it tries each backend in order and returns the first that yields events, so a paid tier or an outage never breaks collection.

Backend fallback chain

OrderBackendAuth
1API PRO — api-pro.ransomware.live/victims/recentHeader X-API-KEY (from api_key); tried first only when a key is set.
2API v2 — api.ransomware.live/v2/recentvictimsFree, no auth.
3posts.json — data.ransomware.live/posts.jsonFree legacy dump.

Whichever backend serves the data, every record is normalised to the same canonical raw keys so templates behave identically. The raw.backend field records which one answered (pro / v2 / posts).

Configuration

sources:
  ransomware_live:
    enabled: true
    lookback_days: 30                 # fetch attacks up to 30 days old
    api_key: ${RANSOMWARE_API_KEY}    # optional PRO tier; else v2 → posts.json

Event fields

FieldValue
sourceransomware.live
title{victim} by {group}
urlStable ransomware.live permalink (falls back to the leak URL)
tags["ransomware"]
raw.victimVictim name
raw.group_nameRansomware group name
raw.countryVictim country (ISO-2 code)
raw.country_displayFull country label — e.g. France (FR). Falls back to the raw code when unknown, empty when absent.
raw.country_flagFlag emoji computed from the ISO-2 code — e.g. 🇫🇷. Empty for an invalid/empty code.
raw.activityVictim sector / group activity
raw.websiteVictim domain
raw.discoveredDiscovery date
raw.attackdateAttack date

Enrichment

Whichever backend serves a record, it is enriched with derived fields so the cards render consistently:

  • Country. country_display (e.g. France (FR)) and country_flag (🇫🇷) are computed from the ISO-2 country code via cassandra_cti/countries.py — a full ISO-3166 name map plus a regional-indicator flag builder. Unknown codes fall back to the raw code; empty codes yield empty strings.
  • Infostealer. ransomware.live's infostealer field is a rich object — users / employees / third-parties counts plus a per-stealer-family breakdown in infostealer_stats — not a boolean. It is condensed into infostealer_summary (e.g. 886 users, 32 employees, 251 third-parties) and infostealer_stealers (top families, e.g. Lumma (137), RedLine (132)). Both stay empty when every count is zero — the API attaches the object even when it correlated nothing, so this avoids a false positive. The card renders the real counts and top stealer families only when they are non-zero.
  • Leak link. leak_url is the group's onion leak site (when the backend provides it). The event url stays the stable ransomware.live permalink so dedup identity does not shift on a fallback; the cards link both the permalink and the leak site.

The title country-flag emoji is detected from the event URL TLD — 🇫🇷 🇬🇧 🇩🇪 🇺🇸 🇨🇦 ... — and prepended when emojis: true. This is separate from the raw.country_flag field above, which is derived from the ISO-2 country code.

Transports

Microsoft Teams

Sends Adaptive Cards (MessageCard format) to a Teams incoming webhook. Supports single-event and batched delivery.

Example connector

connectors:
  - id: "teams-cert"
    type: "teams"
    params:
      webhook_url: ${MSTEAMS_WEBHOOK_CERT}
      theme_color: "0078D7"
      emojis: true
      throttle_ms: 1000
      batching:
        enabled: false
        max_items: 10

Payload format (MessageCard)

{
  "@type": "MessageCard",
  "@context": "http://schema.org/extensions",
  "themeColor": "0078D7",

Telegram

Sends messages to a chat/channel via the Telegram Bot API (sendMessage). Unlike Teams/Discord there is no incoming-webhook URL — you need a bot_token and a chat_id.

Example connector

  - id: "telegram-soc"

Setup

  1. Create a bot with @BotFather → /newbot → copy the token.
  2. Add the bot to your channel/group as an administrator.
  3. Use the public @channelusername, or read result[].message.chat.id from getUpdates for a numeric id.
  4. Test it live: cassandra doctor connector --id telegram-soc.

Rendering, limits and retries

  • Messages render as HTML (parse_mode: HTML); the card title is emitted as <b>…</b> by the transport, the body from a per-route template.
  • Text is truncated at the Telegram 4096-char limit.
  • On 429 it honours Telegram's retry_after and backs off; 5 retry attempts with exponential backoff.

Email (SMTP)

Sends HTML email through any SMTP server (Gmail, SendGrid, a corporate relay…). Uses the Python standard-library smtplib run in a worker thread so it never blocks the event loop — no extra dependency.

Example connector

connectors:
  - id: "email-soc"
    type: "smtp"
    params:
      host: ${SMTP_HOST}            # e.g. smtp.gmail.com
      port: 587
      security: "starttls"          # starttls (587) | ssl (465) | none (25)
      username: ${SMTP_USERNAME}
      password: ${SMTP_PASSWORD}    # app password / API key
      from_addr: ${SMTP_FROM}       # defaults to username
      to_addrs: ${SMTP_TO}          # "a@x.com,b@y.com" or a YAML list
      subject_prefix: "[CTI]"
      batching: { enabled: true, max_items: 20 }   # optional digest emails

Message format

  • Subject: subject_prefix + the event/source title.
  • Body: a multipart/alternative message — plain text (tags stripped) plus HTML rendered from templates/smtp_default.j2 (or a custom per-route template).
  • security selects the connection: starttls (587, default), ssl (implicit TLS, 465), or none (plaintext relay on 25). Login is skipped when username/password are omitted.
  • A recipient (to_addrs) is required; sending without one raises a configuration error.

Gmail example: host smtp.gmail.com, port 587, security starttls, username = your address, password = a Google App Password (not your login password). Enable batching to get one digest email instead of one per event.

Setup & test (one-time)

1. Run the bridge — device linking needs json-rpc mode and outbound network:

docker run -d --name signal-api -p 8090:8080 --dns 9.9.9.9 \
  -v $HOME/.local/share/signal-api:/home/.local/share/signal-cli \
  -e MODE=json-rpc bbernhard/signal-cli-rest-api

2. Link it to your Signal account as a secondary device (your phone stays primary — no number takeover):

curl -s -o signal-qr.png "http://localhost:8090/v1/qrcodelink?device_name=cassandra-cti"
xdg-open signal-qr.png   # phone: Signal -> Settings -> Linked devices -> + -> scan

3. Confirm the link, then send a test:

cassandra doctor connector --id signal-soc

If linking fails with "Connection closed", the container has no internet — check docker exec signal-api getent hosts chat.signal.org. A common cause is a host firewall dropping the Docker bridge's forwarded traffic (allow forwarding for docker0). Alternatively you can register a dedicated number as a new primary (POST /v1/register/{number} + SMS/captcha) — never with your personal number.

Messages are plain text (URLs auto-link), so leave Signal routes template-less or use a plain-text template — a Markdown/HTML card would show its markup literally.

Supply-chain note. CassandraCTI's Signal transport is a thin HTTP client — it imports no Signal library and vendors no bridge code, so there is no code-level dependency on the bridge (it's an external process behind api_url). To harden the bridge itself: pin the image by digest (…@sha256:… instead of :latest), or self-build from a reviewed fork. The transport works unchanged against any of them.

Routing

Routing Rules

Routes match incoming events and determine which transports receive them. Every matching route fires — a single event can fan out across several routes at once (e.g. a "firehose" route alongside a topic route). Per-transport deduplication guarantees the same event is never delivered twice to the same transport, even when overlapping routes target it. Events not matched by any route are silently dropped.

Match by source prefix

routes:
  - name: "all-rss"
    include_sources: ["rss:"]          # matches rss:CERT-FR, rss:Krebs, ...
    transports: ["discord-alert"]

Match by exact source

routes:
  - name: "ransomware"
    include_sources: ["ransomware.live"]
    transports: ["teams-soc"]

Match by tag

routes:
  - name: "cert-only"
    include_tags: ["cert"]
    transports: ["teams-cert", "discord-alert"]

Match by regex

routes:
  - name: "critical-cves"
    include_regex: "(?i)(critical|zero.day|0-day|CVE)"
    transports: ["teams-soc", "discord-alert"]

Regex is tested against both title and source. You can combine matchers: a route matches if any of its configured criteria match the event.

Fan-out to multiple transports

routes:
  - name: "cert-alerts"
    include_tags: ["cert"]
    transports: ["teams-cert", "discord-alert", "teams-mgmt"]  # all three receive it

With a custom template

routes:
  - name: "ransomware-rich"
    include_sources: ["ransomware.live"]
    transports: ["teams-soc"]
    template: "templates/ransomware_card.j2"

AI & Automation

Briefings

Routes deliver each event. A briefing does the opposite: periodically it recaps a batch — the LLM writes a short, prioritised summary with links, sent through a normal transport after the individual alerts. A shift hand-over: "here's what came in, and what matters."

briefings:
  - name: vuln-daily
    include_sources: ["cisa.kev"]   # same selectors as routes (OR; omit all = everything)
    include_tags: ["cert"]
    transports: ["discord-brief"]   # a connector id (must be in transports.use)
    schedule: "24h"                 # 24h | 6h | 30m | 2d
    min_items: 1                    # skip if fewer than N new items
    max_items: 40                   # cap what the LLM sees
    template: "templates/briefing_default.j2"   # telegram -> briefing_telegram.j2
KeyDefaultMeaning
include_sources / include_tags / include_regex—select events like a route (OR across them; none = all)
transports—connector id(s) that receive the brief
schedule24hhow often it may fire
min_items1don't send with fewer than N new items
max_items40cap on items fed to the LLM
templatebriefing_default.j2Markdown for Discord/Teams; briefing_telegram.j2 for Telegram

Each cycle, after delivery, a briefing checks whether its schedule elapsed; if so it gathers the events ingested since its last run that match its selectors, has the LLM prioritise them (KEV / ransomware-linked / high-confidence IOCs first) and narrate them with links, sends one message and records the timestamp. Trigger manually with briefing-run:

cassandra briefing-run --all            # force every briefing now
cassandra briefing-run --name vuln-daily
cassandra briefing-run --all --dry-run  # [DRYRUN:BRIEFING], no LLM call

Briefings need the LLM layer to resolve a provider. With none available they're skipped (a warning is logged) — everything else runs.

Operations

Running Continuously

The single most important thing to understand: deduplication is what makes "only send new items" work — not a flag. Every run reloads the config, fetches every source, and the SQLite store remembers what has already been delivered to each transport. Each pass therefore sends only items that were never delivered — run the same command a hundred times and each article goes out exactly once.

reload config → fetch all sources → filter → DEDUP (SQLite) → route → deliver

The store keeps this delivery history for store.seen_ttl_days (default 90) before purging older entries.

One-shot vs. loop

# One pass and exit — ideal behind cron or a systemd timer
cassandra run --config config.yaml --connectors connectors.yaml

# Stay alive and repeat every N seconds (default 300 = 5 min)
cassandra run --config config.yaml --connectors connectors.yaml --loop --interval 300

In --loop mode the process reloads config.yaml at the start of every cycle, so adding a feed or editing a route is picked up on the next pass — no restart needed. RSS and ransomware.live share the exact same fetch → dedup → deliver cycle.

First run: avoid the backlog flood

On a fresh database the first pass sees every item currently in your feeds as "new" and would send the whole backlog at once. Seed with a date floor, then let dedup take over:

# 1) Seed: only recent items, sent once
cassandra run --config config.yaml --connectors connectors.yaml --since 2026-07-05

# 2) Then run continuously — dedup prevents any repeats
cassandra run --config config.yaml --connectors connectors.yaml --loop --interval 300
  • dedup (always on) — never re-sends a delivered item. Bypass for testing with --no-dedupe.
  • --since YYYY-MM-DD — an optional date floor; most useful on the first run.
  • filters.max_items_per_source (config) — caps how many items each feed emits per cycle.

Ransomware & PRO feeds

Same model. sources.ransomware_live.lookback_days controls how far back the source looks on each fetch; dedup guarantees each victim is delivered once, so in loop mode every newly-disclosed victim goes out on the next cycle. The PRO feeds (ransomware_press, ransomware_8k, ransomware_stats) run through the identical cycle — ransomware_stats deduplicates per day, so you get one digest daily.

Deduplication

Event IDs are generated as SHA1(source + canonical_url + title). This makes IDs deterministic and stable across restarts. Two SQLite tables track state:

  • events — stores event metadata with first/last seen timestamps
  • deliveries — tracks per-transport delivery status (ok / failed)

An event is only sent to a transport if it has no successful delivery record for that transport. Using --no-dedupe or setting CTI_NO_DEDUPE bypasses this check.

Async concurrency

All source fetches run concurrently as asyncio tasks. Transport sends are sequential per route (respecting throttle delays) but multiple routes can fan out to different transports. The event loop is created fresh for each cassandra run invocation; loop mode calls run_once() in a sleep-loop.
